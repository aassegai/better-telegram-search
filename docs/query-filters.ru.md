# Фильтры поиска и варианты обязательных слов

[English](query-filters.md)

Здесь описаны действующие фильтры и варианты для будущего выбора. Поля
обязательных/исключённых слов и язык модификаторов **не реализованы и не
утверждены**. `+слово`, `-слово`, `from:` и `in:` сейчас не являются операторами.

## Что уже есть

| Потребность | Интерфейс и API задач (`SearchSpec`, версия 1) | Пробел или граница |
| --- | --- | --- |
| Чат | Выбор в боковой панели; `scope.mode: all/selected`, `scope.chat_ids` | Пустой `selected` означает ни одного чата. Используются устойчивые ID, не названия. |
| Автор | Селектор; `author_ids` | UI выбирает одного автора, API допускает несколько. Источник пересылки задаётся отдельно. |
| Период | Даты; `date_from`, `date_to` | UTC, начало включительно; конечная дата без времени включает весь указанный день. |
| Точная фраза | Чекбокс; `exact_phrase` | Нормализованная буквальная фраза в сообщении/OCR. Визуальное сходство не доказывает наличие фразы. |
| От кого переслано | Чекбоксы с поиском; `forwarded_from` | Названия из метаданных архива могут не иметь ID аккаунта. Выбранные источники — альтернативы. |
| Содержимое | Селектор; `content_type` | API поддерживает текст/фото/служебные сообщения. Аудиотипы относятся к отдельной реализации аудио. |
| Удалённые | Чекбокс; `exclude_deleted` | Условие учитывается в совпадениях и показываемом контексте. |
| Обязательные/исключённые слова | Отдельного контрола нет | Нужен выбор интерфейса и области проверки. |

Разные категории пересекаются, значения внутри списка — альтернативы. Для
текстового чанка одно собственное сообщение должно одновременно удовлетворять
автору, дате, типу и пересылке. Заимствованный контекст не подтверждает эти
условия. Фильтры изображения/OCR проверяются по владельцу вложения.

Пустой запрос показывает сообщения только по кнопке/Enter. Непустая строка из
стоп-слов не превращается в просмотр архива. Смена фильтров не запускает поиск.

## Варианты для последующего выбора

| Вариант | Пример RU / EN | Компромисс |
| --- | --- | --- |
| Отдельные поля «Обязательно» / «Исключить» | Запрос `поездка`, обязательно `Казань`, исключить `самолёт`; `trip`, `York`, `flight` | Условия видны, синтаксис учить не нужно; форма занимает больше места. |
| Модификаторы с chips | `поездка +Казань -самолёт`; `trip +York -flight` | Быстрый ввод; нужны кавычки, escaping, ошибки и разрешение неоднозначных имён. Сейчас такой синтаксис не действует. |
| Назначение роли введённому слову/фразе | Ввести `поездка Казань самолёт`, отметить роли двух последних слов | Нет служебных символов; сложнее поведение при редактировании, повторяющихся словах и фразах. |

При утверждении любой вариант должен компилироваться в один типизированный
запрос. Обязательные условия ограничивают корпус до top-K, включая ANN.
Этот документ не выбирает один из вариантов.

## Примеры для согласования семантики

Пусть существуют:

1. `Поездка в Казань поездом` / `A trip to York by train`.
2. `Поездка в Казань: самолёт` / `A trip to York by flight`.
3. `Поездка в Самару` / `A trip to Bath`.
4. `Казань` / `York`, а в соседнем сообщении — `самолёт` / `flight`.

Предполагаемые условия: запрос `поездка` / `trip`, обязательно `Казань` / `York`,
исключить `самолёт` / `flight`. Здесь `самолёт` и `самолётом` не следует молча
считать одним токеном: выбор целого слова, подстроки и словоформ ещё предстоит.

| Режим | Предлагаемое поведение после выбора области и способа буквального совпадения |
| --- | --- |
| По словам | №1 проходит при совпадении всех значимых слов запроса; №2 исключается только если выбранное правило действительно сопоставляет исключённый термин; №3 не содержит обязательного. |
| По смыслу | Обязательные/исключённые слова остаются жёсткими буквальными условиями. Смысловая близость не обходит их. |
| Слова и смысл | Одинаковые жёсткие условия в обеих ветках, затем объединение рангов. |

№4 показывает нерешённую границу: при проверке по одному сообщению слово соседа
не исключает совпадение, при проверке по всему чанку — может исключить. Его
релевантность запросу — отдельный вопрос. Размер показываемого контекста никогда
не должен менять допустимость результата.

Также нужно выбрать:

- Проверять опорное сообщение или собственный текст всего индексируемого чанка.
- Считать OCR/транскрипт отдельным доказательством или объединять с подписью
  владельца. Не брать текст другого файла или сообщения.
- Подтверждать текстовые условия картинки подписью, OCR, обоими или никак.
  Одного визуального сходства недостаточно для буквального условия.
- Требовать целый токен или подстроку; определить поведение фраз и словоформ.
- Учитывать ли заимствованный reply-контекст. Показываемых соседей предлагается
  обсуждать отдельно от доказательства совпадения.

## Стоп-слова и требования к будущему parser

Текущий lexical требует **все** значимые термы; автоматического OR нет.
Стоп-слова удаляются только из обычной lexical-части, включая OCR. Они
сохраняются в embedding-запросе и точной фразе. Будущие явно обязательные и
исключённые термы также должны обходить фильтрацию стоп-слов.

| Запрос | Действующее поведение |
| --- | --- |
| `это всё про жёлтый велосипед` | Требуются `желтый` и `велосипед`. |
| `where is the red bicycle` | Требуются `red` и `bicycle`. |
| `не работает wi-fi 42` | Отрицание, части технического термина и число сохраняются. |
| `can't O'Reilly v2` | Сохраняются компоненты отрицательного сокращения, имени и короткий термин. |
| `the and is` / `и в это` | Объяснение отсутствия значимых слов; предложение смыслового поиска или точной фразы. |
| Точная фраза `the and is` | Поиск фразы без удаления стоп-слов. |
| Пустой текст | Просмотр по выполненным фильтрам без моделей. |

Нормализация lexical: Unicode NFKC, casefold, `ё → е`. Будущий parser должен
обрабатывать апострофы, дефисы, Unicode, URL, кавычки, escaping, неизвестные
операторы и неверные даты. Нельзя удалять похожее на `from:` содержимое из URL
или цитаты без разбора. Условия строки и UI не перетирают друг друга молча:
нужно правило объединения внутри категории и видимый список применённых условий.
Названия чатов/авторов разрешаются в устойчивые ID с явной обработкой
неоднозначности.
