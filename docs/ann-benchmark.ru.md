# Сравнение ANN на реальных текстовых эмбеддингах

[English](ann-benchmark.md) · [Реализация поиска](ann-retrieval.md)

`scripts/benchmark_ann_embeddings.py` сравнивает cosine IVF_FLAT, IVF_HNSW_SQ и
IVF_HNSW_FLAT на эмбеддингах BERTA для сгенерированных русских текстов. Используются
закреплённые ONNX-модель, токенизатор, префиксы, masked-mean pooling и нормализация
из приложения; инференс — только CPU. Это проверка индексов, а не качества поиска
по Telegram с человеческой разметкой.

## Полученные результаты

[Полный отчёт](benchmarks/ann-embeddings.json): Linux x86_64, LanceDB 0.39.0,
ONNX Runtime 1.30.0, четыре CPU-потока. Получены 8192 различных float32-вектора
размерности 768; подготовка вместе с запросами заняла 343,451 с. Время инференса
не входит в замеры поиска. В каждой области — 16 запросов.

| Индекс | Сборка, с | Все файлы индексов, МиБ | Sampled RSS процесса сборки, МиБ | Native warm p50/p95 всего набора, мс, 32 probes |
| --- | ---: | ---: | ---: | ---: |
| IVF_FLAT | 0,472 | 24,24 | 484,7 | 38,015 / 44,137 |
| IVF_HNSW_SQ, refinement 4 | 0,551 | 7,54 | 431,4 | 40,152 / 45,280 |
| IVF_HNSW_FLAT | 0,822 | 25,55 | 474,6 | 34,069 / 36,612 |

На всём наборе recall равен 1,0 для всех настроек. С фильтрами картина другая.
Средний strict recall@10 при 32 probes:

| Область | Доступных векторов | IVF_FLAT | IVF_HNSW_SQ | IVF_HNSW_FLAT |
| --- | ---: | ---: | ---: | ---: |
| Текст | 6553 | 1,00000 | 1,00000 | 1,00000 |
| OCR-текст | 1639 | 1,00000 | 1,00000 | 1,00000 |
| Один чат | 2048 | 1,00000 | 1,00000 | 0,98125 |
| Узкая дата текста | 703 | 1,00000 | 1,00000 | 1,00000 |
| Автор | 1170 | 1,00000 | 1,00000 | 1,00000 |
| Источник пересылки | 2731 | 0,99375 | 1,00000 | 0,99375 |
| Комбинация | 293 | 0,99375 | 0,95000 | 0,93750 |

Худший отдельный запрос при 32 probes: соответственно 0,9, 0,2 и 0,0; последние
два провала относятся к маленькой комбинированной области. При 8 probes худшие
средние по scope: 0,55625, 0,68750 и 0,70000. При 64 probes все области и запросы
дали 1,0. Все три индекса вернули 16 из 16 заранее известных свежих результатов;
канонические удаления оставались исключены.

Настоящий путь приложения с IVF использовал exact для узкой даты и комбинации.
При 32 probes последующий p50 по всей базе — 59,512 мс. Для источника пересылки
понадобилось шесть ограниченных native-запросов: p50 приложения — 217,616 мс,
а p50 исходного exact-прохода — 54,530 мс. Это разные проходы, а не парное warm-
измерение ускорения. Результат указывает на дорогую работу scope/IPC и не доказывает
ускорения приложения. Меньшего размера SQ-индекса недостаточно для выбора HNSW.

## Воспроизведение

В отдельном uv-окружении установите закреплённые semantic-зависимости и подготовьте
публичную модель в выделенной папке бенчмарка:

```sh
uv sync --locked --extra semantic
uv run --no-sync python - <<'PY'
from pathlib import Path
from telegram_search.config.model_registry import model_spec
from telegram_search.inference.bundles import BundleStore
BundleStore(Path('/tmp/bts-ann-benchmark')).prepare(model_spec('berta'))
PY
uv run --no-sync python scripts/benchmark_ann_embeddings.py
```

Полная команда для трёх кандидатов рассчитана на LanceDB 0.39.0. Закреплённая для
macOS Intel версия 0.25.3 поддерживает IVF_FLAT/IVF_HNSW_SQ, но не IVF_HNSW_FLAT;
ошибка неподдерживаемого типа не является результатом измерения recall.

Сам бенчмарк проверяет локальные файлы модели и ничего не скачивает. Вторая
допустимая папка — `workspace/benchmarks/ann` в репозитории, через
`--model-workspace`. Произвольные пути к моделям, ссылки/junction отклоняются.
Пути к архивам и рабочей базе не принимаются; приложение запускать не нужно.
Источник — публичная синтетическая relevance-фикстура и детерминированные шаблоны.

По умолчанию: 8192 различных текста и 16 запросов-перефразировок. Доступны
4096–32768 строк, 4–24 запроса и 1–8 CPU-потоков. Все кандидаты используют одни
хеши входа/векторов, embedding space и запросы. Для каждого создаются отдельный
spawn-процесс, SQLite и LanceDB во временной папке. Лимит кандидата — 900 секунд;
прерванный процесс завершается через kill/join до удаления папки. Стоимость
инференса измеряется отдельно от поиска.

Публичный отчёт записывается только в `docs/benchmarks/ann-embeddings.json`;
другой путь допустим в ignored `workspace/` или `plans/`. Заменяется только JSON
со своим маркером версии. Запись атомарная. В отчёте — агрегаты, версии и хеши,
без текстов, запросов, ID авторов и локальных путей.

## Измерения

В общей таблице есть текст и строки с меткой смыслового OCR. Строятся 64 cosine-
партиции, проверяются 8, 32 и 64 probes. HNSW: `m=20`, `ef_construction=300`,
`ef=128`; SQ уточняет четырёхкратный набор кандидатов по исходным векторам.
Размер — сумма файлов native `_indices`, включая scalar-индекс ID. RSS сборки
сэмплируется для всего процесса с библиотеками и входными векторами.

Через общий код canonical prefilter/merge приложения проверяются:

- Весь набор, только текст, только OCR и один чат.
- Узкая дата текстовых строк, автор, источник пересылки, сочетание чат/автор/дата.
- Свежие неиндексированные векторы и канонические удаления после сборки индекса.

SQLite проверяет максимум 512 ID за раз. Coarse predicate применяется только
после доказательства соответствия всей области; иначе native top-K вызывается с
ограниченными ID prefilters. Ответ проверяется снова; выход за scope прерывает
опыт. Оба режима используют один read snapshot на область. Эталон — настоящий
`VectorStore.exact_filtered` приложения.

`recall_at_10` — доля ID из точного top-10, попавших в ANN, с делением на реальное
число точных результатов. Это не полнота по человеческим оценкам смысла.
Близкие float32-дистанции могут менять порядок у границы. Все партиции — контроль,
а не целевая настройка ускорения. Сохраняются средняя и минимальная полнота по
запросам; хорошее среднее одной области не компенсирует провал другой.

Warm p50/p95 считаются по второму native-проходу вместе с metadata proof, SQLite,
несколькими ограниченными запросами и merge. Первый вызов записан отдельно,
но **не является OS-cold**: импорты, запись и exact-эталон уже могли прогреть кэши.
Время exact взято из прохода построения эталона.

Только совместимый IVF_FLAT дополнительно проходит настоящий dispatcher и
дочерний query-процесс приложения. Первый вызов включает старт процесса;
дальше отдельно записаны p50/p95, recall, фактическая стратегия и причина fallback.
Для маленьких областей приложение выполняет exact, хотя native-эксперимент всё
равно проверяет ANN. In-process время HNSW нельзя называть задержкой приложения.
RSS дочернего query-процесса не входит в RSS родителя.

Для проверки свежего хвоста намеренно добавляются query-role векторы с заранее
известным ближайшим результатом. Каждый должен попасть в top-10 без перестройки.
Два вектора остаются на диске, но удаляются из канонической области. Это тест
включения хвоста и фильтрации, а не качества поиска новых passage-текстов.

## Ограничения и решение

Повторяющиеся сгенерированные темы не воспроизводят распределение реального
архива. OCR-строки — готовые тексты без распознавания. Таблица свидетельств
представляет опубликованные векторы и не проверяет production joins чанков с
сообщениями или условия одного сообщения. SigLIP-изображения и аудио не измерены.
Обучение native-центроидов не имеет общего закреплённого seed/набора между сборками:
разницу при малом числе probes нельзя приписывать только графу или квантованию.
Для каждого кандидата одна сборка на одном хосте, без доверительных границ по
повторным опытам. Top-100, большие корпуса и OS-cold замеры приложения ещё нужны.

Полный exact остаётся значением по умолчанию. Для смены индекса/default нужны
более широкие текстовые и настоящие визуальные нагрузки, замеры больших областей
и явная проверка качества отдельно по scope. Этот отчёт сам по себе не выбирает
HNSW и не подтверждает релевантность Telegram-поиска.

Контракты upstream: [LanceDB Python API](https://lancedb.github.io/lancedb/python/python/)
и [Lance scanner/prefilter](https://lancedb.github.io/lance/api/py_modules.html).
