# Переранжирование текста и OCR через Jina

[English](jina-reranking.md) · [Миграция моделей](model-migration.md)

Jina v2 — дополнительная парная модель для уточнения порядка английских текстовых
и OCR-результатов. Для русского рекомендуется Giga; существующий выбор сохраняется.
Язык интерфейса меняет рекомендацию, а не выбранную модель. Reranker не меняет
текстовое embedding space и не требует перестройки индекса.

## Включение

1. Откройте **Настройки → Модели → Уточнение результатов**.
2. Выберите **Jina v2 · Английский** и нажмите **Сохранить настройки модели**.
3. Нажмите **Подготовить Jina**: приложение проверит/скачает закреплённые файлы и
   выполнит локальный smoke test. Папка и размер загрузки показаны в карточке.
4. Включите **Переранжирование Jina** и сохраните. Подготовка сама его не включает.

Выбор, подготовка и включение — разные действия. Перед сменой профиля нужно
дождаться текущей подготовки. Ошибка подготовки остаётся видимой и не считается
готовностью. Базовый поиск доступен, когда reranking выключен, не подготовлен
или превышает лимит памяти.

Модель [jinaai/jina-reranker-v2-base-multilingual](https://huggingface.co/jinaai/jina-reranker-v2-base-multilingual/blob/9cfeff2df7d40d1b78e75e5e9cebec92a99813c9/README.md)
закреплена на `9cfeff2df7d40d1b78e75e5e9cebec92a99813c9`. Лицензия весов —
**CC-BY-NC-4.0 для некоммерческого использования**; коммерческое использование
регулируется отдельными условиями модели. Условие видно до подготовки; загрузка
необязательна.

## Вычисления и ограничения

Официальный FP32 ONNX и соответствующие tokenizer/config-файлы занимают
1 131 141 915 байт, примерно 1079 МиБ. Каждый проверяется по размеру и SHA-256.
Приложение не скачивает и не исполняет Python-код модели. Runtime остаётся
ONNX Runtime/tokenizers, без Torch. Доступна подготовка из проверенного локального
кэша без сети.

В отличие от независимых эмбеддингов Giga, Jina получает настоящую пару запрос/
документ в формате XLM-RoBERTa `<s>A</s></s>B</s>`. Один logit преобразуется в
float32 sigmoid score: больше — релевантнее. Это не индексный вектор; Jina никогда
не передаётся текстовому индексатору.

- До 50 уже отфильтрованных кандидатов на каждую ветку текста/OCR. Батч не больше
  четырёх пар и настроенного текстового батча.
- Запрос ограничен 512 токенами, пара — 1024. После ограничения запроса усекается
  только документ. До токенизации: максимум 8192 символа запроса и 32768 документа.
- Усечение запроса/кандидатов отражено в метаданных и предупреждении. Агрегация
  скользящих окон длинного документа не реализована.
- Проверяются стабильные ID, количество, форма и конечность оценок. При равенстве
  сохраняется исходный порядок. Изображения и точная фраза обходят reranking;
  необработанный хвост сохраняет порядок перед существующим объединением веток.
- Ограниченный кэш учитывает модель, revision архива/настроек и полные хеши запроса
  и документа. Другой запрос не использует чужую оценку. «Показать ещё» читает
  готовую выдачу и не запускает Jina повторно.

Фильтры автора/даты/чата/пересылки и доступность источника проверяются до и после
инференса. Отмена отбрасывает поздние оценки до кэширования/публикации. Смена профиля
или включения увеличивает сохраняемый revision: возврат к прежнему выбору во время
поиска не позволяет опубликовать результат под другой моделью. История сохраняет
manifest фактически применённого reranker.

Jina наследует устройство текстовых запросов, CPU-потоки и лимиты RAM/VRAM. Сессия
выгружается после настроенного простоя. Перед загрузкой проверяется память; ошибка
сохраняет базовый порядок с объяснением. На этом хосте проверен CPU, CUDA/CoreML
не запускались. Для GPU выполняется проверка оценок относительно CPU. Явный GPU
при ошибке сообщает её; Auto может перейти на CPU до вычисления оценок.

## Реальные CPU-пробы и воспроизведение

[Публичный отчёт](benchmarks/jina-cpu.json): Linux x86_64, ORT 1.30.0, четыре потока.
Четыре простых авторских запроса (три EN, один RU) поставили нужного кандидата первым.
Разница оценки отдельно и в padded-батче — ноль. Длинная пара ограничена, оба флага
усечения выставлены.

Первый вызов вместе с загрузкой занял 4,686 с. Двенадцать последующих коротких
батчей по четыре пары: p50 113,081 мс, p95 157,727 мс. Sampled peak RSS всего
процесса вместе с длинной парой — примерно 1,82 ГиБ. Проверка файлов не входит
в эти интервалы. Поиск, SQLite, UI и прикладной кэш не измеряются; это не прогноз
пропускной способности на длинных фрагментах. Четыре smoke-запроса не подтверждают
релевантность Telegram-поиска или порог качества.

[Проверка runtime](benchmarks/jina-runtime-parity.json) выполнена также на ORT 1.23.2
в отдельном uv-окружении. Для того же bundle и 16 пар максимальная разница с ORT
1.30.0 — `2,3841858×10⁻⁷`; padding и длинная пара прошли обе версии. Это проверка
совместимости, а не GPU или качества поиска. Второй запуск шёл параллельно тестам,
поэтому его время не используется для сравнения скорости.

Подготовьте публичные файлы в отдельной папке и запустите:

```sh
uv run --no-sync python - <<'PY'
from pathlib import Path
from telegram_search.config.model_registry import rerank_spec
from telegram_search.inference.bundles import BundleStore
BundleStore(Path('/tmp/bts-jina-runtime')).prepare(rerank_spec('jina-v2'))
PY
uv run --no-sync python scripts/benchmark_jina.py
```

Сам скрипт проверяет локальные файлы и ничего не скачивает. Вторая разрешённая папка
моделей — `workspace/benchmarks/jina`, через `--model-workspace`. Архив и рабочая БД
не принимаются; ссылки/junction отклоняются. Публичный отчёт заменяется только
своим форматом с маркером версии; другой вывод — в ignored `workspace/` или `plans/`.
Используются общие ограниченные JSON/атомарная запись. В публичном отчёте — версии,
хеши, агрегаты и синтетические оценки, без локальных путей и пользовательских данных.

UltraBERT и пользовательские адаптеры остаются отдельной частью реализации.
Встроенный парный адаптер не обещает запуск произвольного checkpoint.
