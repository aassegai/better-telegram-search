# Архитектура

Реализованы lexical baseline, lifecycle обновлений и CPU dense/hybrid: FastAPI,
SQLite/FTS5, ONNX Runtime, LanceDB и React/TypeScript/Vite. Python 3.11–3.13;
на доступной машине используется 3.12.3 вместо предложенного в плане 3.11. uv.lock
фиксирует зависимости, frontend использует единственный npm package-lock.json.
PyTorch отсутствует в runtime; для численной проверки существует отдельное uv-окружение `validation/`.

SQLite — источник истины. `storage/schema.sql` создаёт схему версии 1;
`storage/migrations/002_lifecycle.sql` обновляет её до версии 2, `003_semantic.sql` — до 3. Миграции выполняются
в одной транзакции под межпроцессной блокировкой, существующие сообщения сохраняются.
`schema_migrations` фиксирует версию; неподдерживаемые версии отвергаются.
FTS5 имеет external content и транзакционные триггеры. `rebuild` восстанавливает FTS
из сообщений. База работает в WAL, штатное завершение делает checkpoint.

Один сервер и один writer на workspace: межпроцессный FileLock и общий RLock для
регистрации импорта, управления задачами и удаления. Импорт идёт в одном фоновом
потоке, не задерживая поисковые запросы. Транзакция содержит максимум 100 сообщений
и checkpoint. ijson читает JSON потоково; метаданные и SHA проверяются отдельными
потоковыми проходами. При resume файл сканируется до checkpoint, пропущенные записи
не сохраняются в памяти. На больших JSON это линейное чтение, а не seek по offset.
Пауза/отмена прекращают импорт у границы батча; уже записанные сообщения остаются.

Ключ диалога: `(scope, external_id)`. Ключ сообщения: `(chat_id, message_id)`.
Без ID требуется явное создание нового диалога либо привязка к существующему.
Экспорт одного диалога поддержан; общий экспорт аккаунта с `chats.list` пока отвергается.
Родные Unix timestamps имеют приоритет; naive ISO-даты без epoch трактуются как UTC.
Текст массива entities разворачивается без потери отображаемого текста; полный исходный
объект, включая entities/reply/пересылки/альбомы/служебные события, остаётся в SQLite.

Корни экспортов записываются в SQLite относительно workspace, а не копируются.
Несколько корней могут принадлежать одному диалогу. SHA-256 файлов вычисляется
потоково, один blob связан со всеми отправками. Отсутствующие, повреждённые и опасные
пути отмечаются без прекращения импорта. Восстановление отсутствовавшего файла не
считается редакцией текста. При различных известных хешах файла возникает конфликт.
Источник приложения не удаляется при удалении диалога; общий blob удаляется только
после исчезновения последней ссылки. `compact` удаляет orphan blobs и выполняет VACUUM.

BM25 пока индексирует **отдельные сообщения** — разрешённый планом lexical baseline.
Служебные события сохраняются, но не индексируются. Нормализация: NFKC, casefold,
ё→е; unicode61 без Porter. Обычный запрос требует все слова (AND). Пользовательский
ввод превращается в литеральные термы, операторы FTS не исполняются. Точная фраза
дополнительно требует непрерывного совпадения нормализованного исходного текста.
Лучшие `bm25` значения меньше; scores не выдаются как вероятность релевантности.

Фильтры действуют одновременно на одно найденное сообщение. Соседи — контекст,
помеченный, если он не проходит фильтры. Карточка включает 2 сообщения до и 3 после,
сокращаясь на краях диалога. Уже показанные anchor IDs соседних карточек исключаются;
это начальная дедупликация, не будущая полноценная кластеризация dense windows.

Сервер слушает 127.0.0.1, проверяет Host/Origin/Fetch Metadata; мутации требуют
случайный session token. React выводит переписку как текст. Медиа доступны по ID;
пути проверяются после resolve, включая symlinks. MIME определяется по raster format,
SHA повторно проверяется, CSP sandbox и nosniff запрещают активное содержимое.
Медиа больше 32 МиБ не выдаются через API. Вложения кроме фото хранятся как ссылки,
но не отдаются через браузер. URL произвольного файла отсутствует.

`ImportService` использует `PreviewService` для потокового предварительного отчёта.
Staging в SQLite содержит классификацию, входящую запись, медиа и версию исходного
сообщения; канонические сообщения при проверке не меняются. Применение проверяет
SHA JSON и ревизию диалога, затем использует зафиксированные staging-батчи. Resume
не пересчитывает классификацию уже проверенных записей. Каждый следующий батч
проверяет версии затрагиваемых сообщений. Конфликты сохраняются отдельно;
Медиа перед каждым применяемым батчем, включая resume, проверяются заново:
изменение содержимого или доступности файла останавливает задачу до записи батча.
`ConflictService` возвращает обе редакции и CAS token в одном read snapshot.
Явный выбор версии и состояние конфликта записываются в одной транзакции.

`index_segments` хранит поколения каждого `(chat_id, UTC-день)`. Изменение сообщения
или ссылки на медиа атомарно повышает target generation и создаёт запись `index_work`.
При переносе времени сообщения обновляются старый и новый день. Предыдущие работы
сегмента становятся superseded; неизменённый импорт не меняет поколения.
Lexical generation сразу соответствует message FTS. CPU worker потоково строит чанки
каждого изменившегося дня в отдельном поколении. До embedding измеряется число чанков
и токенов; прогресс батчей сохраняется. Lance upsert стабильных IDs предшествует SQLite
checkpoint: после сбоя повтор не дублирует векторы. Публикация проверяет source generation
и embedding space под общим lifecycle lock. Старые поколения исключаются из поиска;
durable cleanup удаляет устаревшие векторы, а compact очищает старые Lance versions.
Удаление диалога оставляет durable tombstone; при reimport того же ID он удаляется
до записи любых новых векторов. Snapshot строителя освобождается до SQLite compaction.

Чанки содержат до 8 сообщений, перекрытие около 4, максимум 480 model tokens с авторами,
prefix и photo markers. Разрывы: диалог, UTC-день, часовой интервал. Длинный текст
делится по исходным Unicode ranges, без скрытого model truncation; оригинал сохраняется.
Hybrid BM25 и cosine используют одни и те же опубликованные чанки. Каждый кандидат
имеет одно canonical сообщение, одновременно проходящее все фильтры. SQL whitelist
поступает в Lance до top-k; IDs идут батчами по 512, top100 хранится в ограниченной heap.
RRF k=60 с равными весами объединяет списки. Exact выбран после сравнения с ANN.
Карточка показывает все исходные сообщения чанка и по одному соседу (до 10 сообщений).

Python разделён по ответственности:

- `storage`: SQLite, миграции, ревизии и поколения индексов.
- `backend`: FastAPI и локальные HTTP-контракты.
- `ingestion`: импорт, предварительные отчёты, разрешение конфликтов.
- `search`: lexical/dense/hybrid retrieval, чанки, фильтры, LanceDB и контекст.
- `indexing`: фоновая очередь, generations/checkpoints, модельная подготовка и CLI.
- `inference`: проверенные наборы, локальный tokenizer и CPU ONNX encoder.
- `config`: валидируемые настройки CPU, manifest registry и диагностика.
- `security`: защита путей, symlink boundaries и правила приватности Git.
- `shared`: нормализация текста и ошибки приложения.

Корневой `cli.py` — точка входа команды `telegram-search`.

Проверка lifecycle этапа на Linux/WSL: 36 Python-тестов, 7 Chromium e2e,
Ruff и production frontend build прошли. Default frontend route после переноса
пакетов проверен отдельно. Локальная база с 221 сообщением обновлена с v1 до v2;
повторный preflight: 221 unchanged, 0 added/updated/conflicts, исходники не изменены.
